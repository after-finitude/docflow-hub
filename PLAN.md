# Docflow Hub — план разработки

Проект: **Docflow Hub** — AI Document Operations Hub по ТЗ №1 v2 от 2026-08-02. Покрывает полный объём: обязательный (этапы 1–8) и второй этап (этап 9) с одинаковой детализацией.

---

## 0. Зафиксированные решения (сверх ТЗ)

| Вопрос                             | Решение                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| LLM-провайдер                      | DeepSeek V4 Flash через OpenAI-совместимый API: реализация `OpenAICompatibleLLMProvider` с настраиваемыми `base_url`, `api_key`, `model`. Покрывает DeepSeek, OpenAI и любой совместимый endpoint одной реализацией. ⚠️ Отклонение от ТЗ (там зафиксированы OpenAI/Anthropic) — согласовать с владельцем ТЗ. Поддержку strict JSON-схем у DeepSeek проверить в начале этапа 4; repair-политика из ТЗ 6.4 подстраховывает в любом случае |
| ORM                                | Drizzle ORM + drizzle-kit для миграций. Кастомный SQL (uuidv7-defaults, REVOKE для AuditEvent) — обычными SQL-миграциями drizzle-kit                                                                                                                                                                                                                                                                                                    |
| Структура репозитория              | Монорепозиторий (npm workspaces): `apps/web` (Next.js), `apps/api` (NestJS HTTP), `apps/worker` (NestJS standalone-приложение, отдельный контейнер), `packages/core` (инфраструктура NestJS, общая для api и worker: конфигурация, схема БД, хранилище, очереди), `packages/shared` (типы, контракты и чистые модули без зависимости от фреймворка: validation engine, evidence→bbox, confidence)                                    |
| Очереди                            | Отдельная BullMQ-очередь на каждый этап pipeline (`preprocess`, `ocr`, `classify`, `extract`, `validate`, `export`) — даёт настраиваемый параллелизм по этапам (ТЗ 6.10)                                                                                                                                                                                                                                                                |
| PDF→PNG миниатюры и рендер для OCR | pdfjs-dist в Node (worker) → sharp. Без внешних бинарников в контейнере                                                                                                                                                                                                                                                                                                                                                                 |
| Генерация демо-документов          | HTML-шаблоны → PDF через Playwright (chromium в dev-зависимостях, не в рантайм-образе); искажения сканов через sharp                                                                                                                                                                                                                                                                                                                    |

Принцип из ТЗ, определяющий порядок работ: **сначала весь pipeline на mock-провайдерах до зелёного сквозного E2E, потом реальные провайдеры**. Mock-и детерминированы и живут рядом с фикстурами.

Главный технический риск — модуль **evidence → bbox** (ТЗ 6.5). Он выделен в чистый пакет без зависимостей от NestJS и прототипируется на OCR-фикстурах в начале этапа 4, до интеграции с LLM.

## 1. Архитектура

### 1.1. Компоненты

```
┌─────────┐   HTTP    ┌─────────┐   jobs    ┌──────────┐
│ apps/web│ ────────► │ apps/api│ ────────► │  Redis   │
│ Next.js │ ◄──SSE─── │ NestJS  │           │  BullMQ  │
└─────────┘           └────┬────┘           └────┬─────┘
                           │                     │
                      ┌────▼─────┐         ┌─────▼─────┐
                      │ Postgres │ ◄────── │apps/worker│──► GCV OCR
                      │    18    │         │  NestJS   │──► DeepSeek LLM
                      └──────────┘         └─────┬─────┘──► Google Sheets
                                                 │
                                            ┌────▼───┐
                                            │ MinIO  │
                                            └────────┘
```

- `apps/api` — HTTP API, auth, SSE, синхронная перевалидация при правках, постановка задач в очереди.
- `apps/worker` — потребители очередей: preprocess (миниатюра, нормализация), OCR, классификация, извлечение + evidence→bbox, валидация, экспорт. Отдельный контейнер (ТЗ, стек).
- `packages/shared` — код, который обязан работать и в api (синхронная валидация при PATCH поля), и в worker: validation engine, evidence→bbox matcher, расчёт confidence, zod-схемы типов документов, canonical JSON builder.

### 1.2. Pipeline и статусы документа

```
upload ──► Received ──► Processing ──► Needs review ──► Approved ──► Exported
                │           │              │  ▲            │
                ▼           ▼              ▼  │            ▼
             Rejected     Failed        Rejected      (export failed:
          (битый файл)  (после retry)                статус остаётся
                                                     Approved,
                                                     export_status=Failed)
```

Этапы внутри Processing: `preprocess → ocr → classify → extract → validate`. Каждый шаг пишет `WorkflowRun` (attempts, correlation_id, error_code, тайминги). Переход в Approved автоматически — только если нет blocking-ошибок **и** все критичные поля выше порога (ТЗ 6.7); иначе Needs review.

- Retry транзиентных ошибок (OCR/Classification/Extraction): BullMQ `attempts: 3`, кастомный backoff 1с/5с/25с. Repair-политика невалидного JSON от LLM (до 2 повторов) — внутри extract-джоба, отдельный счётчик.
- Экспорт автоматически не ретраится — только ручной повтор (ТЗ 6.10).
- Смена типа / Reprocess / правка поля перезапускают соответствующий хвост pipeline; правка поля выполняет валидацию **синхронно в api** и возвращает обновлённые проблемы в ответе PATCH (ТЗ, API).

### 1.3. Ключевые контракты (проектируются на этапе 1, до кода pipeline)

- `OCRProvider`: `recognize(file, pages) → { pages: [{ pageNumber, width, height, text, blocks: [{ text, bbox, confidence }] }] }`. Формат bbox — как у Google Cloud Vision (вершины полигона → нормализуем в прямоугольник + сохраняем размеры страницы, чтобы фронтенд масштабировал оверлеи).
- `LLMProvider`: `classify(pagesText) → { document_type, confidence, alternatives[], multi_document_suspected }`; `extract(schema, pagesText) → { fields: [{ name, raw_value, normalized_value, evidence: { text, page } | null }] }`.
- `DestinationAdapter`: `export(canonicalJson, mapping, exportKey) → { status, externalRef }`.
- У каждого интерфейса рабочая + mock-реализация; mock-и детерминированы, читают фикстуры по checksum файла.

## 2. Этапы

### Этап 1 — Скелет: монорепо, БД, очередь, хранилище, auth

**Работы:**

1. Монорепозиторий: workspaces, TypeScript 7 (при проблемах тулинга — пакет совместимости tsc6 рядом, без даунгрейда), ESLint, Prettier, tsconfig-пресеты.
2. docker-compose: postgres:18, redis, minio, api, worker, web; `example.env` без секретов; healthchecks.
3. Drizzle-схема всех сущностей из ТЗ §7 (User, Document, Page, Field, ValidationIssue, DocumentSchema, Export, WorkflowRun, AuditEvent). Все id — `uuidv7()` (DB default). `tenant_id` — поле-заглушка с единственным значением.
4. SQL-миграция ролей БД: роль приложения без UPDATE/DELETE на `audit_event` (запись есть, изменение — нет); отдельная роль для миграций.
5. BullMQ: регистрация очередей, воркер поднимается standalone-приложением, конфиг параллелизма per-queue из env.
6. MinIO-клиент: bucket-инициализация, put/get, подписанные ссылки с TTL 15 минут (ТЗ §11).
7. Аутентификация: `POST /auth/login`, `POST /auth/logout`, JWT в httpOnly cookie, глобальный guard (все эндпоинты кроме логина), guard по роли для админ-действий. Seed: оператор + администратор.
8. Каркас Next.js 16.2: layout, страница логина, `proxy.ts` для проксирования API, защита роутов.

**Результат (DoD):** `docker compose up` поднимает всё; вход работает; миграции и seed выполняются; попытка UPDATE на audit_event под ролью приложения падает.

**Статус: реализовано.** Проверки собраны в `npm run verify` — статика (типы, линтер, форматирование, сборка веб-приложения) и поведение поднятого стека (миграции, seed, неизменяемость журнала, вход через веб-порт, отсутствие цикла редиректов, ограничение перебора пароля). Статическая часть проходит; прогон на стеке требует Docker и на машине разработки ещё не выполнялся.

**Отклонения от изначального замысла этапа:**

- Добавлен пакет `packages/core` — инфраструктура NestJS (конфигурация, схема БД, хранилище, очереди), общая для `api` и `worker`. В `packages/shared` остался только код без зависимости от фреймворка, который нужен и фронтенду.
- Вместо ESLint используется **oxlint**: typescript-eslint несовместим с TypeScript 7, а пакета `tsc6` из ТЗ в реестре npm не существует. Подробности и остальные последствия TS 7 — в `known-limitations.md`.
- Имя session-cookie и роль БД приложения зафиксированы константами, а не переменными окружения: одинаковое значение в двух независимых процессах через окружение не обеспечить (сборка Next выполняется без `.env`), а расхождение давало бы отказ без диагностики.
- Строки подключения к БД собираются из компонентов в `env.ts` вместо готовых URL в окружении — чтобы пароль не хранился в двух местах.
- Сверх объёма добавлены `GET /auth/me` (нужен фронтенду для отрисовки шапки), ограничение частоты попыток входа по логину, ревалидация роли в БД на каждый запрос и колонки `ip`/`user_agent` в журнале.

### Этап 2 — Приём документов и Inbox

**Работы:**

1. `POST /documents`: multipart, лимит 25 МБ, типы PDF/JPEG/PNG, SHA-256, метаданные (имя, mime, размер, источник, received_at), оригинал в MinIO, запись Document со статусом Received, постановка в `preprocess`.
2. Ранняя валидация файла в preprocess-джобе: повреждённый / зашифрованный PDF / неподдерживаемый контент → статус `rejected` с человекочитаемой причиной, **до любого вызова LLM** (ТЗ 6.1, 9, 10).
3. Миниатюра первой страницы (pdfjs-dist → sharp → PNG в MinIO рядом с оригиналом).
4. Дубликат по checksum: связь duplicate, повторно не обрабатывается/не экспортируется (ТЗ §10).
5. `GET /documents` с фильтрами (статус, тип, даты, blocking, источник) и пагинацией; `GET /documents/{id}`; `GET /documents/{id}/file` — подписанная ссылка.
6. SSE `GET /events/stream`: события смены статуса/прогресса этапов; на клиенте EventSource + fallback на polling 5с при недоступности SSE.
7. Экран Document Inbox: таблица по ТЗ 5.1 (превью, имя, источник, тип+уверенность, статус, min confidence критичных полей, счётчик проблем, дата), фильтры, drag-and-drop зона, прогресс этапов для Processing, действие «повторить» для Failed.
8. AuditEvent на все значимые действия начиная с этого этапа (upload, reject, retry).

**Результат (DoD):** файл появляется в Inbox с уникальным id и миниатюрой; битый файл — rejected с причиной; список живёт по SSE (критерии приёмки 1, 9 частично).

**Статус: реализовано.** Проверки этапа добавлены в `npm run verify`: приём PDF, статус после подготовки, миниатюра, подписанная ссылка, отклонение повреждённого файла с причиной, отсечение неподдерживаемого типа, связывание дубликата, фильтр очереди, ответ потока событий. Модуль проверки файла отдельно прогнан на фикстурах `scripts/fixtures/` без Docker: валидный PDF даёт миниатюру и число страниц, повреждённый и подменённый по типу отклоняются.

**Решения этапа:**

- **Растеризация PDF — `mupdf` (WASM), а не `pdfjs-dist`.** pdfjs в Node не умеет растеризовать без реализации canvas, то есть всё равно потребовал бы нативной зависимости. `mupdf` делает и растеризацию, и определение шифрования с повреждением одним API и без нативных бинарников. `pdfjs-dist` остаётся для просмотрщика в браузере на этапе 6 — там canvas родной.
- **Постоянные дефекты файла не бросают исключение.** Повреждённый или защищённый паролем файл переводит документ в `rejected` и завершает задачу успешно: иначе BullMQ трижды перечитывал бы заведомо битый файл. Исключение бросается только на транзиентных ошибках, а статус `failed` выставляется лишь когда попытки исчерпаны.
- **Временный терминал pipeline.** После подготовки документ переходит в `needs_review` — этапы 3–5 вставят перед этим переходом OCR, классификацию, извлечение и валидацию.
- **События между контейнерами — pub/sub Redis.** Статусы меняет воркер, а SSE раздаёт API; это разные процессы, поэтому нужен внешний канал.
- **Миниатюра отдаётся через API, оригинал — подписанной ссылкой.** Для подписи заведён отдельный клиент MinIO с публичным адресом: подпись покрывает Host, и ссылка на `minio:9000` в браузере не открывается.
- **Ключи хранилища** строятся от идентификатора папки, а не от id документа: файл кладётся в хранилище до вставки строки, чтобы запись никогда не указывала на отсутствующий объект. Все файлы документа лежат под общим префиксом — под удаление по retention.

### Этап 3 — OCR и нормализация

**Работы:**

1. Интерфейс `OCRProvider` + `MockOCRProvider` (детерминированные фикстуры: постраничный текст, блоки, bbox, confidence).
2. `GoogleVisionOCRProvider` (@google-cloud/vision 5.x): документный OCR, ru+en, маппинг ответа (полигоны → прямоугольники, confidence блоков, размеры страниц).
3. Нормализация изображений перед OCR: deskew/поворот по метаданным ориентации, повышение контраста при необходимости, отбрасывание пустых страниц (sharp + эвристики; фиксируем ограничения в /known-limitations).
4. Постраничное хранение: таблица Page (текст, блоки с bbox, confidence, width/height); `GET /documents/{id}/pages`.
5. Учёт отправки во внешние сервисы: лог «какие страницы ушли в OCR/LLM» (ТЗ §11), без текста документов в логах.
6. Retry-обвязка транзиентных ошибок (общая утилита для OCR/LLM-этапов).

**Результат (DoD):** сканированный PDF получает постраничный текст и координаты блоков; работает и на mock, и на реальном GCV (критерий приёмки 2).

**Статус: реализовано** (mock-путь проверен исполнением; GCV-путь написан по типам SDK, но против реального сервиса не прогонялся — нет ключа, проверка на этапе 8).

**Решения этапа:**

- **Mock-провайдер — текстовый слой PDF через mupdf, а не фикстуры.** Для
  сгенерированных демо-документов (этап 8) текстовый слой полон, поэтому mock
  выдаёт настоящие блоки с настоящими координатами — на них же будет
  тестироваться evidence→bbox. Блоками становятся строки (не абзацы): матчеру
  нужна построчная гранулярность. Изображениям mock возвращает пустую страницу.
- **GCV получает страницы по одной растровой картинкой** (mupdf → PNG,
  OCR_RENDER_DPI=200): единый путь для PDF и изображений, без обязательного GCS
  для батчевого PDF-режима.
- **Пустые страницы не отправляются провайдеру** (детекция по разбросу
  яркости), но строка Page сохраняется — иначе сдвинулась бы нумерация страниц
  относительно оригинала, на которую ссылаются источники полей.
- **bbox нормализованы к 0..1** относительно размеров страницы; сами размеры
  хранятся в Page. Фронтенд масштабирует оверлеи без знания DPI.
- **Неустранимые ошибки провайдера** (неверный ключ, выключенный API) бросаются
  как UnrecoverableError — BullMQ не тратит на них попытки; транзиентные
  (5xx, лимиты, сеть) идут через обычный retry с backoff 1с/5с/25с.
- **Отправка страниц внешнему провайдеру фиксируется в журнале** (ТЗ §11):
  действие `document.ocr_external`, номера страниц, имя провайдера.

### Этап 4 — Классификация, схемы, извлечение, evidence → bbox

Порядок внутри этапа — сначала п.1 (matcher на фикстурах), это главный риск проекта.

**Работы:**

1. **Модуль evidence → bbox** в `packages/shared`, чистые функции:
   - точное вхождение → нечёткое (нормализация пробелов/регистра, Левенштейн ≤ 15% длины);
   - один блок → его bbox; последовательность соседних блоков → объединённый bbox;
   - найден на другой стране → фактическая страница + снижение confidence + причина;
   - не найден → `source_found=false`, confidence cap 0.6.
   - Unit-тесты на OCR-фикстурах: перенос на две строки, дефисы, разрывы в числах, регистр, пунктуация (ТЗ 6.5).
2. Версионируемые схемы типов (DocumentSchema в БД: json_schema + thresholds + version + is_active). Seed 4 типов: Invoice (по ТЗ §13), Bank statement, Tax letter, Contract — до 15 полей, типы string/number/date/currency/enum/boolean/line_items. `GET /schemas`, `PUT /schemas/{type}/thresholds` (админ).
3. Интерфейс `LLMProvider` + `MockLLMProvider` (фикстуры) + `OpenAICompatibleLLMProvider` (DeepSeek V4 Flash; base_url/model из env). В начале работ — проверка реального поведения DeepSeek на strict JSON; результат фиксируется в /known-limitations.
4. Классификация: OCR-текст первых 2 страниц → тип, confidence, до 3 альтернатив, флаг `multi_document_suspected` (→ warning + Needs review, без автосплита). Порог per-type из thresholds; ниже порога → Unknown → ручной выбор типа; Unknown не экспортируется.
5. Извлечение: промпт по схеме типа; ответ валидируется zod-схемой; невалидный JSON → repair-политика (до 2 повторов) → ручная обработка без потери исходных данных. Обязательный `evidence` (дословный фрагмент + страница) на каждое поле; поле без evidence = поле без источника. Missing = `null` + признак, никаких догадок (ТЗ §9).
6. Сохранение Field: raw_value / normalized_value (ISO-даты, number-суммы, ISO 4217) / confidence / confidence_reason / source_page / source_bbox / source_found / is_critical.
7. `POST /documents/{id}/type` — ручная смена типа с перезапуском извлечения по новой схеме.

**Результат (DoD):** документ получает тип, поля со значениями и bbox-источниками; matcher покрыт unit-тестами по списку из ТЗ 6.5; 4 типа обрабатываются по разным схемам (критерии 3, 4, частично 5).

**Статус: реализовано.** Появился тест-раннер (`npm test`, node:test на скомпилированном выводе): 36 unit-тестов — матчер по списку ТЗ 6.5 (перенос на две строки, дефисы, разрывы в числах, регистр, пунктуация, чужая страница, not found), нормализация значений, расчёт confidence. Полная mock-цепочка (OCR → классификация → извлечение → матчер) прогнана оффлайн на фикстуре: тип invoice 0.95, 8/9 полей с raw→normalized и bbox-источниками, line_items — корректный Missing. Путь через реальный LLM API не прогонялся (ключа нет) — проверка на этапе 8.

**Решения этапа:**

- **Матчер: два прохода (exact по всем страницам, затем fuzzy)** — иначе
  нечёткое совпадение на заявленной странице обгоняло бы точное на
  фактической. Окна до 4 соседних блоков с тремя вариантами склейки: пробел,
  вплотную (разрывы в числах), снятие дефиса переноса. При fuzzy-проходе
  пунктуация и дефисы нормализуются, допуск — Левенштейн ≤ 15% длины.
- **Нормализация значений выполняется кодом, не LLM**: от модели требуется
  дословное значение (verbatim), приведение к типу — детерминированные
  функции с тестами. LLM, «услужливо» нормализующий значение, ломал бы
  сопоставление evidence с текстом документа.
- **Repair-политика внутри LLM-провайдера** (до 2 повторов с описанием ошибок
  валидации в диалоге), исчерпание — `LlmInvalidResponseError`: задача не
  ретраится, документ уходит в needs_review с причиной, исходные данные
  (OCR-страницы) сохранены (ТЗ 6.4, §10).
- **Пороги меняются созданием новой версии схемы**, не правкой активной:
  принятое решение фиксируется вместе с версией правил (ТЗ 6.7), правка
  in-place ломала бы воспроизводимость.
- **Mock-LLM: классификация по заголовочным паттернам, извлечение по шаблону
  «Метка: значение»** демо-набора. Первый вариант с пословными паттернами
  уводил инвойсы в unknown — слово «tax» есть в каждом инвойсе.
- **Терминус сместился на extract** → needs_review; этап 5 вставит валидацию
  и авто-маршрутизацию.

### Этап 5 — Валидация, confidence, маршрутизация

**Работы:**

1. Validation engine в `packages/shared` (работает в worker и синхронно в api): типы проверок — обязательность, regex, диапазон дат, формат валюты, арифметика сумм (`subtotal + tax_total ≈ grand_total`, tolerance 0.02, blocking), справочник значений, условия между полями. Уровни info/warning/blocking. Результат — понятный оператору текст с expected/actual.
2. Правила — в конфигурации при DocumentSchema, версионируются вместе со схемой.
3. Единственная cross-document проверка: уникальность `invoice_number` в рамках поставщика (ТЗ §9, исключение). Других сверок не добавляем.
4. Расчёт итогового confidence поля из сигналов: OCR-confidence области, уверенность извлечения, результат валидации, source_found (cap 0.6 без источника). Чистая функция + unit-тесты.
5. Маршрутизация: авто-Approved только при «нет blocking И все критичные поля ≥ порога»; иначе Needs review. Решение фиксируется в WorkflowRun вместе с версией схемы/правил (воспроизводимость, ТЗ 6.7).
6. Перезапуск валидации по всем триггерам: после извлечения, правки поля, смены типа, Reprocess.

**Результат (DoD):** несходящаяся сумма даёт blocking; документ с критичным полем ниже порога уходит в Needs review (критерии 6, 7 — серверная часть).

**Статус: реализовано.** 59 unit-тестов (23 новых: движок правил и маршрутизация). Оффлайн-прогон на данных реальной mock-цепочки: корректный инвойс проходит автоматически; расхождение сумм, пропуск критичного поля и валюта вне справочника — каждое даёт blocking и отправляет на проверку. В `verify.sh` добавлены проверки автопрохода, blocking по суммам с expected/actual и уникальности invoice_number.

**Решения этапа:**

- **Движок — чистая функция**, `today` передаётся снаружи: решение воспроизводимо
  и тестируемо, а проверка «дата не позже сегодня + 7 дней» не зависит от часов
  машины в момент прогона.
- **Обязательность выводится из `FieldSpec.required`**, а не дублируется
  правилами: конфигурация остаётся одна. Пропуск критичного поля — blocking,
  некритичного — warning.
- **Отсутствующее слагаемое в правиле сумм считается нулём**: не указанный налог
  не повод объявлять суммы несходящимися. Правило молчит, если нет самой
  целевой суммы — об этом скажет проверка обязательности.
- **Сигналы уверенности сохраняются в поле** (`confidence_signals`), и
  перевалидация пересчитывает confidence из них заново. Иначе повторный прогон
  накладывал бы штраф за провал валидации поверх уже применённого.
- **Оркестрация (ValidationRunnerService) живёт в `packages/core`**, потому что
  вызывается из двух процессов: воркером после извлечения и API синхронно при
  правке поля (этап 6).
- **Уникальность invoice_number** — вне чистого движка: единственная
  cross-document проверка требует БД. Реализована в runner отдельным запросом.
- **Перевалидация заменяет только свои проблемы**: предупреждение о нескольких
  документах в одном файле ставит классификация, и перезапуск его не стирает.
- **Решение о маршрутизации пишется в журнал** вместе с id и версией схемы,
  списком id правил и порогами — воспроизводимость по ТЗ 6.7.

### Этап 6 — Review Workspace

**Работы:**

1. Просмотрщик: pdfjs-dist (PDF) / img (JPEG, PNG), зум, поворот, лента миниатюр страниц. Оверлей bbox: полупрозрачные прямоугольники, координаты масштабируются через сохранённые width/height страницы.
2. Связка полей и областей: hover/клик по карточке поля → подсветка области + скролл страницы к ней; «Показать в документе»; для source_found=false — явный признак «источник не найден», без ссылки.
3. Правая колонка: шапка (тип с выпадающим списком смены, статус, счётчик проблем, кнопки Approve/Reject/Reprocess); список полей с сортировкой blocking → низкий confidence → остальные; карточка поля по ТЗ 5.2 (normalized + raw по иконке, число и цветовая полоса confidence, confidence_reason, текст ошибки валидации с expected/actual).
4. Таблица line_items с добавлением/удалением строк.
5. Фильтры полей: Все / Отсутствующие / Низкая уверенность / Ошибки валидации.
6. Редактирование: `PATCH /documents/{id}/fields/{name}` — синхронная перевалидация, ответ содержит обновлённый список проблем и доступность Approve; before/after + пользователь + время в AuditEvent; `is_edited` на поле.
7. Approve (заблокирован при нерешённых blocking — и на UI, и на сервере), Reject (причина из списка + комментарий), Reprocess.

**Результат (DoD):** полный цикл ручной проверки; клик по полю подсвечивает область; правка мгновенно обновляет проблемы и кнопку Approve (критерии 5, 6, 8 — UI-часть).

**Статус: реализовано.** В `verify.sh` добавлены проверки рендера страницы, блокировки Approve при blocking (409), синхронной перевалидации при правке, отметки `isEdited`, пары before/after в журнале, подтверждения после устранения ошибки и отклонения с причиной.

**Решения этапа:**

- **Просмотрщик рендерит страницы на сервере через mupdf, а не pdfjs-dist
  в браузере — отклонение от ТЗ.** Причина техническая: bbox нормализованы
  к размерам страницы, которые сообщил mupdf на этапе OCR; рендер тем же
  движком гарантирует совпадение оверлеев, у другого движка возможны
  расхождения в трактовке CropBox/MediaBox. Побочно отпадает настройка
  worker'а pdfjs в сборке Next.js, которую я не смог бы проверить. Один путь
  работает и для PDF, и для сканов: mupdf открывает изображение как документ
  (проверено).
- **Правка поля не подтверждает документ автоматически.** Валидация после
  правки запускается с `autoApprove: false`: исправив последнюю ошибку,
  оператор не должен обнаружить документ уже подтверждённым — Approve
  нажимает он сам. Для pipeline автопроход остаётся включённым (ТЗ 6.7).
- **Правка очищает сигналы уверенности и ставит confidence = 1.** Сигналы
  извлечения к введённому человеком значению неприменимы; перевалидация
  такое поле не пересчитывает.
- **Approve перепроверяет blocking на сервере**, а не доверяет клиенту:
  блокировка кнопки в интерфейсе — удобство, а не защита (ТЗ §9).
- **Оверлеи позиционируются процентами** от нормализованных координат,
  поэтому не зависят ни от масштаба, ни от разрешения рендера.

### Этап 7 — Канонический JSON и экспорт

**Работы:**

1. Canonical JSON builder (`packages/shared`): не зависит от адаптера; включает правки оператора; версия схемы внутри.
2. Маппинг внутренних полей на поля назначения — в конфигурации.
3. Адаптеры: `FileJsonAdapter` (JSON в MinIO/каталог экспорта), `GoogleSheetsAdapter` (service account, ключ в секретах, append-строка по маппингу).
4. Идемпотентность: `export_key` (unique constraint), повторный запрос с тем же ключом возвращает существующий экспорт (критерий 10).
5. Обработка недоступности destination: документ остаётся Approved, `export_status=Failed`, доступен ручной повтор; авторетраев нет (критерий 11).
6. `POST /documents/{id}/export`; статус Exported после успеха; audit.

**Результат (DoD):** сквозной путь до Google Sheets и JSON-файла; повторный экспорт не создаёт дубликата; сбой destination не ломает Approved.

**Статус: реализовано** (файловый адаптер проверяется в `verify.sh`; Google Sheets написан по типам SDK, против реального API не прогонялся — ключа нет).

**Решения этапа:**

- **Экспорт выполняется синхронно в API, а не через очередь.** Автоповторов
  у экспорта нет по ТЗ 6.10, поэтому главная ценность очереди не используется,
  а оператору важен немедленный ответ о доступности назначения. Очередь
  `export` остаётся зарегистрированной под будущий пакетный экспорт и DLQ
  этапа 9.
- **Ключ идемпотентности по умолчанию — `<documentId>:<destination>`.**
  Повторный запрос находит существующую запись: успешную возвращает как есть
  (второй объект не создаётся, критерий 10), неуспешную повторяет с
  инкрементом попыток. Клиент может передать свой ключ.
- **`generatedAt` канонического JSON передаётся в builder снаружи** — та же
  причина, что и с `today` в валидации: чистая функция и воспроизводимый вывод
  в тестах.
- **Позиции вынесены из `fields` в отдельный блок `lineItems`**: у них своя
  структура, и табличные адаптеры работают с ними иначе, чем со скалярами.
- **Sheets подключается только при заданном ключе.** Иначе запрос падал бы
  внутри вызова API вместо понятного «назначение не настроено».
- **Файловый адаптер не использует маппинг**: канонический вид и есть
  содержимое файла. Маппинг применяется табличными назначениями.

### Этап 8 — Seed, генератор документов, evaluation

**Работы:**

1. Генератор синтетических документов: HTML-шаблоны → PDF (Playwright), 40–60 документов, минимум 8–10 на тип, без реальных ПД; эталоны известны из данных генератора. Состав по ТЗ §13: инвойсы разных форматов, выписка, налоговое письмо, договор, скан низкого качества (поворот+шум+контраст через sharp, рукописная пометка), дубликат, повреждённый файл.
2. Размеченный eval-набор: 15 документов с эталонами критичных полей в репозитории.
3. `npm run eval`: прогон набора через pipeline, метрики по ТЗ §12 (classification accuracy ≥95%, critical field exact match ≥90%, field coverage ≥98%, source coverage и straight-through — как есть, false auto-approval = 0 на eval-наборе, median review time — по данным открытие→Approve). Отчёт в `/evaluation/last-run.md`: метрика, значение, размер набора, дата, версии схем и правил.
4. Итерация по качеству промптов/порогов до целевых значений; изменения порогов — через конфиг/API (экран настроек не строим).

**Результат (DoD):** `npm run eval` печатает отчёт, результат в репозитории, целевые метрики достигнуты или расхождение объяснено (критерий 12).

**Статус: реализовано.** 43 документа (≥9 на тип), 15 размеченных, отчёт в `evaluation/last-run.md`. Все целевые метрики достигнуты на mock-провайдерах; отчёт явно объясняет, что именно это измеряет.

**Решения этапа:**

- **Генератор — pdf-lib, а не Playwright из плана.** Playwright тянет загрузку
  Chromium (~150 МБ) и сеть; нужного качества макета достаточно от прямой
  отрисовки. Кириллица — встроенным DejaVu из npm, без бинарников в репозитории.
- **Генерация детерминирована** (фиксированное зерно ГПСЧ и база дат): корпус
  и эталоны всегда согласованы, повторный запуск даёт те же файлы.
- **Harness прогоняет те же модули, что и прод**: провайдеры, `buildExtractedField`
  с матчером, движок валидации, маршрутизацию. Ради этого логика сборки поля
  вынесена из процессора извлечения в `packages/shared/src/pipeline`. Оценка,
  меряющая копию кода, не измеряла бы ничего.
- **Отчёт честно называет, что измерено.** На mock-провайдерах высокие значения
  означают исправность конвейера, а не качество модели, — это написано в самом
  отчёте, чтобы цифры не читались как оценка LLM.

**Дефект, найденный прогоном:** флаг «несколько документов в одном файле»
создавал предупреждение, но не мешал автопроходу — а ТЗ 6.3 требует отправлять
такой документ на проверку. Исправлено: у проблемы появился признак
`forcesReview`, который учитывают и маршрутизация, и runner.

### Этап 9 — Второй этап объёма

**Работы:**

1. **Второй источник** — папка Google Drive (или почтовый ящик — выбрать при старте этапа по доступности API) с синхронизацией по расписанию (повторяемая BullMQ-задача) и cursor-состоянием. Новые файлы → приём как upload (source_type=Drive/Email, source_path/source_message_id); изменённые → новая версия; удалённые → пометка.
2. **Версионирование**: новый content hash по тому же source_path → новая версия (version_number+1), старая сохраняется, актуальна последняя; изменение файла во время обработки — текущий checksum дообрабатывается, новая версия ставится отдельно (ТЗ §10).
3. **Удаление и retention**: удаление в источнике → `is_active=false`; периодическая задача физического удаления по retention (90 дней, настраивается); TTL временных файлов 24 часа.
4. **Детекция дубликатов**: расширение механики этапа 2 на все источники, связь duplicate, исключение повторного экспорта.
5. **Dead-letter queue**: джобы, исчерпавшие попытки, уходят в DLQ; ручной повтор из DLQ (`POST /runs/{id}/retry`).
6. **Экран Execution Log** (ТЗ 5.3): таблица (документ, этап, статус, длительность, попытки, код ошибки, correlation_id), раскрытие строки (входные параметры, результат, полный текст ошибки, стек), действия (повторить этап, перевести в ручную обработку, открыть документ), фильтры (только ошибки, даты, тип этапа). `GET /runs`.

**Результат (DoD):** документы приходят из второго источника по cursor; версии и дубликаты обрабатываются по ТЗ; упавшая задача видна в Execution Log и повторяется вручную из DLQ.

**Статус: реализовано.** Источник выбирается конфигурацией (`SOURCE_PROVIDER`),
периодические задачи живут в очереди `maintenance`, журнал выполнения доступен
на `/runs` с повтором этапа из DLQ.

**Решения этапа:**

- **Второй источник — Google Drive, а не почтовый ящик.** `changes.list` с
  `pageToken` и есть требуемый cursor: он один сообщает и о новых, и об
  изменённых, и об удалённых файлах. У почты курсор (UIDNEXT) существует, но
  «изменение письма» и «удаление файла в источнике» в ней не выражаются, а
  версионирование по пути источника теряет смысл.
- **Рядом с ним — наблюдаемая папка (`local_folder`).** Та же роль, что у
  mock-провайдеров OCR и LLM: сквозной путь второго источника должен
  проверяться без ключа service account. Google Drive без реального ключа
  прогнать нельзя, и стенд остался бы без единой проверки приёма из источника.
  Папка отдаёт полный снимок, изменения вычисляются сравнением с принятыми
  файлами (`diffSnapshot`); Drive работает по курсору.
- **Приём вынесен в общий `IngestService`** (`packages/core/src/ingest`).
  Загрузка через интерфейс и синхронизация используют один код: иначе
  дубликаты и версии работали бы по-разному в зависимости от того, откуда
  пришёл файл.
- **Курсор хранится в БД, а не в Redis.** Очередь можно очистить или
  пересоздать; точка, с которой источник читается дальше, переживать это
  обязана. Курсор двигается только после прохода без отказов — иначе
  не скачавшийся файл не вернулся бы в приращение никогда.
- **Retention отсчитывается от `deactivated_at`, а не от даты приёма.** Иначе
  документ, удалённый в источнике вчера, но принятый год назад, стирался бы
  немедленно. TTL 24 часа применяется к объектам хранилища, на которые не
  ссылается ни один документ, — это и есть «временные файлы» в нашей
  архитектуре: следствие того, что файл пишется до вставки строки.
- **DLQ пополняется только при исчерпании попыток.** Постоянные дефекты
  (повреждённый файл) в очередь мёртвых писем не попадают: повторять их
  бессмысленно, а разбирать оператору нечего.
- **Приём стал этапом журнала (`ingestion`).** Значение уже было в перечислении
  этапов, но не использовалось; теперь Execution Log показывает цепочку
  с самого начала.
- **Повтор этапа делается новым correlation_id.** Это отдельная попытка,
  и в журнале она должна прослеживаться отдельно от исходной.

**Дефекты, найденные первым прогоном `npm run verify` на живом стеке.**
До этого этапа стек ни разу не запускался (не было Docker), и статические
проверки этих отказов не видели ни одного:

- **Образ вообще не собирался.** В `.dockerignore` шаблон `*.tsbuildinfo`
  не рекурсивный, поэтому состояние инкрементальной сборки с хоста попадало
  в контекст; `tsc -b` считал пакеты собранными и ничего не выпускал, а `dist`
  из контекста исключён. Сборка падала на «нет типов у `@docflow/shared`».
- **Запрос миниатюры убивал процесс API.** Поток из хранилища отдавался при
  `@Res({ passthrough: true })`: Nest завершал ответ по возврату из метода,
  пока поток ещё писал, — `ERR_STREAM_WRITE_AFTER_END` приходил необработанным
  событием `error` и ронял процесс целиком. Дальше весь стек отвечал 500.
- **Счётчики проблем и текущий этап всегда были нулевыми.** Внутри
  sql-шаблона Drizzle печатает колонки без имени таблицы, поэтому связь
  подзапроса `${validationIssues.documentId} = ${documents.id}` превращалась
  в `document_id = id` и разрешалась в `id` самой подзапросной таблицы.
  Условие не выполнялось никогда — без единой ошибки. Затронуты были все пять
  вычисляемых колонок списка, включая индикатор прогресса и минимальную
  уверенность по критичным полям.
- **Подписанная ссылка на оригинал не выдавалась.** Публичный клиент MinIO
  перед подписью выяснял регион, обращаясь к `MINIO_PUBLIC_URL` — адресу для
  браузера, который изнутри контейнера не открывается. Регион теперь
  спрашивается у внутреннего клиента и передаётся публичному готовым.
- **Сам `verify.sh` врал в двух местах.** При `pipefail` код возврата psql
  (отказ в правах — это ошибка) отменял успешное совпадение `grep`, и три
  проверки неизменяемости журнала читались наоборот. Проверка «неподтверждённый
  документ не экспортируется» обращалась к переменной до присваивания, а при
  `set -u` это оборвало бы прогон на середине.

Три скриншота — [docs/screenshots](docs/screenshots/README.md). Они снимаются
с живого стека командой `npm run screenshots`, а не рисуются вручную: снимок,
который нельзя воспроизвести, устаревает молча. Скрипт управляет уже
установленным в системе браузером и ничего не скачивает — то же решение, что
и в генераторе демо-набора. Отказ для журнала выполнения воспроизводится
удалением объекта из хранилища: это транзиентная ошибка, поэтому попытки
исчерпываются штатно и задача уходит в DLQ.
