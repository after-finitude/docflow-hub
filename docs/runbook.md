# Runbook

Запуск, остановка, повтор упавшей задачи и восстановление (ТЗ §16).

## Запуск

```bash
cp example.env .env
```

Заполнить пароли и `JWT_SECRET` (не короче 32 символов), затем:

```bash
docker compose up --build -d --wait
```

Веб-приложение — http://localhost:3000, API — http://localhost:3001,
консоль MinIO — http://localhost:9001.

Порядок запуска задан зависимостями: миграции и seed выполняет одноразовый
контейнер `migrate` под ролью-владельцем, приложения стартуют только после его
успешного завершения.

Полная проверка живого стека:

```bash
npm run verify
```

## Остановка

```bash
docker compose down          # контейнеры, данные сохраняются
docker compose down -v       # вместе с томами: БД, очереди и файлы стираются
```

## Ежедневные операции

### Документ завис в обработке

Посмотреть текущий этап и его состояние в Execution Log (`/runs`) с фильтром
по документу. Живое состояние очередей:

```bash
docker compose logs worker --tail 100
```

### Повтор упавшей задачи

1. Открыть `/runs`, включить фильтр **только ошибки**.
2. Развернуть строку: там входные параметры этапа, полный текст ошибки и стек.
3. **Повторить этап** — задача ставится заново с новым `correlation_id`,
   запись в DLQ помечается повторённой.

Повторяются `preprocess`, `ocr`, `classification`, `extraction`, `validation`.
Приём не повторяется — это означало бы перечитывание источника. Экспорт
повторяется со страницы документа и никогда автоматически (ТЗ 6.10).

Если автоматический путь безнадёжен, кнопка **В ручную обработку** переводит
документ в `needs_review` с сохранением всех извлечённых полей — дальше с ним
работает оператор.

Целиком с начала pipeline документ перезапускается кнопкой **Повторить**
в Inbox (`POST /documents/{id}/reprocess`).

### Что лежит в dead-letter queue

```bash
docker compose exec postgres psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c \
  "select step, error_code, attempts, failed_at, retried_at
     from dead_letters order by failed_at desc limit 20"
```

Постоянных дефектов там не бывает: повреждённый файл получает `rejected` без
записи в DLQ, потому что повторять его бессмысленно.

### Синхронизация источника

Проход выполняется при старте воркера и дальше по
`SOURCE_SYNC_INTERVAL_SECONDS`. Принудительный проход:

```bash
docker compose restart worker
```

Состояние источника:

```bash
docker compose exec postgres psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c \
  "select source, last_sync_at, last_error from source_cursors"
```

Непустой `last_error` означает, что проход завершился с отказами и **курсор
не сдвинулся**: файлы вернутся в следующее приращение. Повторная обработка
безопасна — приём идемпотентен по паре путь+содержимое.

## Восстановление

### Провайдер недоступен (OCR, LLM)

Транзиентные отказы повторяются сами: 3 попытки с задержками 1с, 5с, 25с.
После исчерпания попыток документ виден в Inbox как `Ошибка`, задача — в DLQ.
Когда провайдер вернётся, задачи повторяются из Execution Log; массово —
через `POST /documents/{id}/reprocess` по списку.

Аварийное переключение на детерминированные провайдеры без внешних вызовов:

```bash
# в .env
OCR_PROVIDER=mock
LLM_PROVIDER=mock
```

```bash
docker compose up -d worker
```

Качество извлечения при этом падает до уровня mock — способ годится, чтобы
не копить очередь, но не для промышленной обработки.

### Назначение экспорта недоступно

Документ остаётся `approved`, запись экспорта получает `failed`. Автоматических
повторов нет: экспорт повторяет оператор кнопкой на странице документа.
Повторный запрос с тем же `export_key` не создаёт второй объект.

### Redis потерял данные

Очереди восстанавливать не нужно: курсор источника лежит в БД, а документы,
застрявшие в `processing`, перезапускаются кнопкой **Повторить**. Расписание
периодических задач создаётся заново при старте воркера.

Найти застрявшие:

```bash
docker compose exec postgres psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c \
  "select id, original_filename, status, received_at from documents
    where status in ('received','processing') order by received_at"
```

### Файл в хранилище пропал

Обработка падает с `storage_unavailable`. Оригинал не восстанавливается —
документ следует отклонить и загрузить файл заново. Ссылки на пропавшие
объекты вычищает retention-задача по TTL.

### Забыт пароль администратора

Роль БД и пароли пользователей приложения не связаны. Пересоздать
seed-пользователей с новыми значениями из `.env`:

```bash
docker compose run --rm migrate npm run db:seed -w @docflow/core
```

Смена `APP_DB_PASSWORD` после инициализации кластера требует `ALTER ROLE`
вручную: роль создаётся только при первичной инициализации.

## Чего делать нельзя

- **Править или удалять строки `audit_events`.** У роли приложения нет таких
  прав, и это защита, а не неудобство: журнал — доказательная база решений.
- **Чистить `dead_letters` до разбора.** Это единственное место, где остались
  входные параметры упавшей задачи и стек.
- **Удалять документы напрямую из БД.** Файлы в хранилище останутся сиротами;
  правильный путь — пометить неактуальным и дать сработать retention.
